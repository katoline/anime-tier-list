## 概要とゴール

今期アニメの画像を週1回自動で取り込み、ユーザーがドラッグ&ドロップでティア表を作って保存・公開・SNS共有できるサイトを、Cloudflare上にほぼ静的な構成で作ります。ページの大半はエッジキャッシュから返し、データベースに触れるのは保存・公開時だけにすることで、アクセスが増えても負荷とコストがほぼ増えない形を狙います。

**MVP（最初のリリース）に含めるもの**

- 季節ごと（冬・春・夏・秋）の作品一覧と画像の週次自動更新（GitHub Actions → PR → 自動マージ）
- ティア表エディタ（ドラッグ&ドロップ、スマホのタッチ操作対応、未ログインでも端末内に自動保存）
- Google / メールアドレスでのログイン、ティア表の保存・公開・URL共有
- 公開ティア表ごとのOGP画像（Xなどでカード表示される画像）
- 季節ページ・作品ページなどSEO用の公開ページと、広告枠

**MVPの後に回すもの**: みんなの集計ランキング、いいね・フォロー、コメント、過去シーズンの一括取り込み。

## 技術スタックとアーキテクチャ

Astro（SEOに強いHTML中心のフレームワーク）をCloudflare Workers上で動かし、エディタ部分だけReactで動かす構成を推奨します。公開ページはJavaScriptがほぼ不要なので表示が速く、検索エンジンにも正しく読まれます。

```
GitHub Actions（週次） ──画像──> R2 ──> CDN ──┐
        │ PR → 自動マージ → デプロイ          │
        ▼                                     ▼
Cloudflare Workers（Astro） <── エッジキャッシュ <── 利用者
        │            │
        ▼            ▼
       D1      Queues / Cron（OGP 画像生成・集計）
```

閲覧はエッジキャッシュで完結し、WorkersとD1に届くのはキャッシュ切れと保存・ログインだけです。

| 役割 | 採用案 | 理由 |
| --- | --- | --- |
| フロント / SSR | Astro + React（エディタのみ） | 静的生成とSSRをページ単位で使い分けられる |
| ドラッグ&ドロップ | dnd-kit | タッチ・キーボード操作に対応 |
| ホスティング | Cloudflare Workers（静的アセット付き） | Pagesの後継。エッジで実行 |
| データベース | Cloudflare D1（SQLite）+ Drizzle ORM | ユーザー・ティア表・作品マスタ |
| 画像保管 | Cloudflare R2 + カスタムドメイン | 転送量課金なし。作品画像とOGP画像 |
| キャッシュ | Cache API / CDN、必要に応じてKV | 公開ページをエッジから返す |
| 非同期処理 | Cloudflare Queues + Cron Triggers | OGP画像生成、集計の定期実行 |
| 認証 | Better Auth（D1対応） | Google OAuthとメールのマジックリンク |
| メール送信 | Resend（またはCloudflare Email Service） | ログインリンク送信 |
| ボット対策 | Turnstile + Rate Limiting | 登録・保存・公開を守る |
| OGP画像 | Satori + resvg（WASM） | Worker内でPNGを生成 |
| データ取得 | GitHub Actions（Node.js + sharp） | 週次で取得→PR→自動マージ |

Next.js（OpenNext経由）も動きますが、Workersのサイズ制限やビルドの複雑さを考えると、この規模ではAstroの方が軽く済みます。

## 作品データと画像の週次取得

画像を「検索して拾う」のではなく、アニメデータベースのAPIから今期作品と画像URLをまとめて取る方式を推奨します。画像検索は精度が不安定で、無関係な画像や転載画像を拾うリスクが高いためです。

**データ取得元の候補**

| 取得元 | 得られるもの | 弱点 |
| --- | --- | --- |
| [AniList API](https://docs.anilist.co/)（GraphQL） | 季節指定で作品一覧、カバー画像、バナー画像、日本語タイトル | 利用規約上、商用利用（広告収益を含む）は事前の問い合わせが必要なはず。要確認 |
| [Annict API](https://developers.annict.com/) | 日本語タイトル、公式サイトURL、放送情報。日本の作品に強い | 画像の網羅率は低め。アクセストークンが必要 |
| [Jikan](https://jikan.moe/)（MyAnimeList非公式API） | 季節一覧と画像 | 非公式。MALの規約にも影響される |
| しょぼいカレンダー | 放送日程 | 画像はない |

推奨は「作品一覧と画像はAniList、日本語表記や公式サイトはAnnictで補完」です。いずれも商用利用の可否を開発前に問い合わせます。

**週次ワークフローの流れ**

1. 毎週月曜 4:00 JST（cron `0 19 * * 0`）にGitHub Actionsが起動。手動実行も可能にする
2. 今日の日付から季節を判定（冬1–3月、春 4–6月、夏 7–9月、秋 10–12月）し、APIから作品一覧を取得
3. リポジトリ内の `data/seasons/2026-fall.json` と差分を取り、新規・変更分だけ処理
4. 画像を取得し、sharpでWebPに変換（エディタ用 160px、詳細用 480px）してR2へアップロード。画像本体はリポジトリに入れず、JSONにはR2のパスと出典だけを書く
5. JSONを更新したブランチでPRを作成（peter-evans/create-pull-request）
6. CIがJSONスキーマ検証・画像の存在確認・件数の急変チェック（例: 前回比で半分以下なら失敗）を実行
7. チェックが通れば `gh pr merge --auto` で自動マージ
8. mainへのマージでデプロイが走り、作品マスタをD1へ同期、季節ページのキャッシュをパージ

**実装上の注意**

- 標準の `GITHUB_TOKEN` で作ったPRでは他のワークフロー（CI）が起動しないため、GitHub AppのトークンでPRを作ります。
- 自動マージにはリポジトリ設定の「Allow auto-merge」と、mainのブランチ保護（必須チェック）が必要です。
- タイトルの手動修正や「この作品は除外」を `data/overrides.json` で上書きできるようにし、自動更新で消えないようにします。
- 前季から続く2クール目の作品も今期に含めるかは「決めてほしいこと」に載せています。

## 画像の著作権と利用規約

キービジュアルやカバー画像の著作権は制作委員会などの権利者にあり、APIから取れることと使ってよいことは別です。広告で収益を得る以上、ここがこの計画で一番大きなリスクです（法的助言ではないので、公開前に専門家への確認を推奨します）。

- **複製と公衆送信**: 画像をR2に保存して配信すると複製・公衆送信に当たります。日本には米国のフェアユースのような広い例外はなく、ティア表の並べ方は「引用」の要件（主従関係など）を満たしにくいです。
- **ホットリンクも安全ではない**: 保存せずAPI側のCDNに直接リンクする方法もありますが、取得元の規約違反や負荷の問題が残り、権利関係が解決するわけではありません。
- **広告審査**: Google AdSenseは権利を持たない画像を中心にしたサイトを審査で落とすことがあります。テキストの独自コンテンツ（作品解説、集計結果）を厚くすることが審査通過にも効きます。
- **OGP画像**: 他人の画像を合成した新しい画像を生成・配信するので、同じ課題がそのまま乗ります。

**推奨する対応**

1. 開発前に取得元APIへ商用利用の可否を問い合わせる
2. 画像は小さいサムネイルのみを保持し、作品名・©表記・公式サイトへのリンクを必ず付ける
3. 削除依頼フォームを設け、`data/overrides.json` で即日非表示にできるようにする
4. 画像が使えない作品でも成り立つよう、「タイトルだけのカード」でもティア表を作れる設計にする
5. 将来的には配信サービスのアフィリエイトや公式プレス素材など、利用条件が明示された画像への切り替えを検討する

## 機能仕様

**ティア表エディタ**

- 初期ティアは S / A / B / C / D。ティア名・色・段数（最大10段）は編集可能
- 画面下部に「未分類」トレイを置き、今期の作品が並ぶ。ドラッグで各ティアへ移動し、ティア内の並び順も保存
- スマホでは「タップで選択→ティアをタップで配置」も併用（小さい画面でのドラッグは誤操作が多いため）
- 未ログインでも使え、編集内容は端末のlocalStorageに自動保存。ログイン時にアカウントへ引き継ぐ
- 編集中はサーバー通信しない。「保存」押下時に1回だけデータを送る（負荷対策の要）
- 画像としてダウンロード（ブラウザ内で生成）

**認証**

- Googleログイン（OAuth）と、メールアドレスにログインリンクを送るマジックリンク方式。パスワードは持たないので漏えいリスクと「パスワードを忘れた」対応が不要
- セッションはHttpOnly Cookie。メール送信前にTurnstileでボットを弾く
- 登録時にユーザー名（公開URLに使う、例: `/u/tonosaki`）と表示名を設定
- 退会とデータ削除をセルフで行えるようにする

**保存・公開・共有**

- 1ユーザーが1シーズンに複数のティア表を持てる（例: 「1話切り時点」と「最終評価」）
- 公開範囲は、非公開 / リンクを知っている人のみ / 公開（一覧や検索に載る）の3段階
- 公開ページ `/t/{短いID}` はサーバーでHTMLを作りエッジにキャッシュ。「このティア表をもとに自分も作る」ボタンで拡散を促す
- X・LINE・Blueskyの共有ボタンとURLコピー。スマホではWeb Share APIを使う

**OGP画像**

- 公開・更新時にQueue経由で 1200×630 のPNGを生成し、R2に保存。ページの `og:image` はそのURLを指す
- リクエストごとに生成しないので、SNSで拡散してもCPU負荷が増えない
- 画像には各ティアの上位数作品・シーズン名・サイト名を入れる（画像が使えない場合はタイトル文字のみ）

## データモデル（D1）

ティア表の中身は1行のJSONとして保存し、保存・表示ともに1回の読み書きで済むようにします。集計は定期ジョブがまとめて計算します。

| テーブル | 主な列 | 備考 |
| --- | --- | --- |
| users | id, username, display_name, avatar_url, created_at | 認証系のテーブル（sessions, accounts, verifications）はBetter Authが作成 |
| seasons | id（例: 2026-fall）, year, season, starts_on | 季節マスタ |
| anime | id, slug, title_ja, title_romaji, image_key, source, source_id, official_url, credit, hidden | 週次ワークフローが同期 |
| season_anime | season_id, anime_id, sort_order | 2クール作品は複数の季節に属せる |
| tier_lists | id, user_id, season_id, title, visibility, tiers_json, ogp_key, created_at, updated_at | tiers_json にティア定義と作品IDの並びを保存 |
| anime_stats | season_id, anime_id, avg_score, count, tier_distribution_json, updated_at | 公開ティア表から定期集計 |
| takedown_requests | id, anime_id, reason, contact, status, created_at | 削除依頼の管理 |

`tiers_json` の例: `{"tiers":[{"label":"S","color":"#ff7f7f","items":[123,456]}],"unranked":[789]}`

## SEO戦略

検索流入の主力は「2026秋アニメ ティア表」「今期アニメ おすすめ」のような季節キーワードと作品名です。そのため、エディタよりも季節ページと集計ページを充実させるのが効果的です。

| URL | 内容 | 検索での役割 |
| --- | --- | --- |
| `/` | 今期のティア表作成への入口、人気の公開ティア表 | サイト名・「アニメ ティア表」 |
| `/seasons/2026/fall` | 今期の作品一覧、みんなの集計ティア、作成ボタン | 「2026秋アニメ」系のメイン |
| `/anime/{slug}` | 作品情報、公式リンク、ティア分布グラフ | 作品名 + 評価 |
| `/t/{id}` | 公開ティア表 | SNSからの流入。作品数が少ないものは noindex |
| `/u/{username}` | ユーザーの公開ティア表一覧 | 基本は noindex |

- 季節ページと作品ページは週次更新時に生成してキャッシュ。本文はすべてHTMLで返し、JavaScriptに頼らない
- 構造化データ（ItemList、BreadcrumbList、TVSeries）、canonical、自動生成のsitemap.xml
- Core Web Vitals対策: 画像はWebP・width/height指定・遅延読み込み、広告枠は高さを予約してレイアウトずれを防ぐ
- 作品ページは画像とタイトルだけでは「薄いコンテンツ」扱いになるため、集計データが一定数たまるまで noindex にする

## 高負荷対策とコスト

方針は「読みはエッジキャッシュ、書きは保存時だけ、重い処理は非同期」です。アクセスの大半はエッジで終わり、D1やWorkerのCPUまで届かない設計にします。

| リクエスト | 処理方法 | キャッシュの無効化 |
| --- | --- | --- |
| 季節ページ・作品ページ | エッジキャッシュ（数時間） | 週次更新・集計更新時にパージ |
| 作品画像・OGP画像 | R2 + CDN（1年、ファイル名にハッシュ） | 不要（更新時は別ファイル名） |
| エディタの作品リスト | 静的JSONをエッジ配信 | 週次更新時 |
| 公開ティア表 `/t/{id}` | 初回のみD1、以降はエッジキャッシュ | 保存・公開範囲変更時にパージ |
| 保存・ログイン | Worker + D1（キャッシュなし） | — |
| みんなの集計 | Cronで毎時1回計算してanime_statsに書く | 計算後にパージ |

- 保存APIにはユーザー単位のレート制限（例: 1分に10回）をかけ、連打やスクリプトを止める
- ティア表は1件数KBなので、100万件保存されてもD1の容量（1データベース10GB）に十分収まる
- 将来書き込みが増えても、季節ごとにD1を分ける、またはDurable Objectsへ移す余地を残す

**コストの目安**: 初期はWorkers Paidプランの月額5ドルで、Workers・D1・R2・Queuesの無料枠を含めてほぼ収まる見込みです。R2は転送量が無料なので、画像がSNSで拡散しても転送費はかかりません。料金体系は変わるため、実装前に[Cloudflareの料金ページ](https://developers.cloudflare.com/workers/platform/pricing/)で改めて確認します。

## 広告配置

広告は閲覧ページ（季節・作品・公開ティア表）に集中させ、ドラッグ操作をするエディタの中には置きません。誤クリックを誘う配置は広告ネットワークの規約違反になりやすいためです。

| ページ | 配置 |
| --- | --- |
| 季節ページ・作品ページ | 見出し下、1画面分以上離した一覧の途中、PCは右サイドバー追従 |
| 公開ティア表 | ティア表の下、共有ボタンの後 |
| エディタ | ドラッグ領域の外（PCのサイドバーのみ、スマホは保存完了画面） |

- 広告ネットワークはGoogle AdSenseを第一候補、審査に通らない場合は国内の忍者AdMaxやi-mobileを代替に。作品ページには配信サービス（dアニメストア、U-NEXTなど）や関連商品のアフィリエイトリンクも相性が良い
- 広告枠は高さを固定してレイアウトずれを防ぎ、スクリプトは遅延読み込みで表示速度を落とさない
- 電気通信事業法の外部送信規律に合わせ、広告・解析ツールの送信先をプライバシーポリシーに明記。欧州からのアクセス向けにはGoogleの同意管理（CMP）を使う
- ads.txtを置き、アドブロック利用者にも機能制限はかけない

## 開発フェーズ

2027年冬アニメ（1月開始）に公開を合わせるのが自然な目標です。各フェーズの期間は1人で開発する場合の目安です。

1. **フェーズ0　準備（1週）**: データ取得元へ商用利用の問い合わせ、ドメイン取得、CloudflareとGitHubの初期設定
2. **フェーズ1　データとエディタ（2〜3週）**: 週次ワークフロー、季節ページ、未ログインで使えるエディタと画像ダウンロード。ここで一度公開して反応を見ることも可能
3. **フェーズ2　アカウントと共有（2〜3週）**: Google・メール認証、保存、公開範囲、公開ページ、OGP画像、SNS共有
4. **フェーズ3　収益とSEO（1〜2週）**: 作品ページ、構造化データ、sitemap、利用規約・プライバシーポリシー・削除依頼窓口、広告申請
5. **フェーズ4　公開後の拡張**: みんなの集計ランキング、いいね・フォロー、過去シーズンの取り込み

広告の審査には数週かかることがあるため、広告なしで先に公開し、審査通過後に広告を有効にする想定です。
